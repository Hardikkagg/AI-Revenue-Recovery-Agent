AI REVENUE RECOVERY AGENT - CURRENT OPERATIONAL MODEL

PURPOSE
-------
This is a sandbox system for failed-revenue events. It detects and normalizes
events, diagnoses failures, estimates recovery probability, selects a safe
strategy, generates bounded text, simulates execution, observes the outcome,
calculates reward, updates an adaptive policy, persists data, and exposes
metrics.

It does not process real payments, recover real production revenue, send real
customer messages, or create real support tickets.

PIPELINE
--------
RecoveryEventInput
  -> detection and normalization
  -> deterministic diagnosis
  -> ML recovery scoring
  -> deterministic safe strategy selection
  -> adaptive policy selection among approved strategies
  -> optional Ollama reasoning/customer message or deterministic fallback
  -> sandbox simulation
  -> observed outcome
  -> reward
  -> in-memory adaptive policy update
  -> SQLite persistence
  -> recovery metrics

RESPONSIBILITIES
----------------
Deterministic rules own input validation, diagnosis, hard safety decisions,
strategy allow-lists, and financial bounds. ML estimates probability. The LLM
generates bounded reasoning and customer copy after strategy selection; it
does not authorize recovery. The simulation layer provides safe local gateway,
communication, escalation, and no-op outcomes.

SCENARIOS AND STRATEGIES
------------------------
Supported event types:
- payment_failure
- checkout_abandonment
- subscription_failure

Available strategies:
- retry_now
- retry_later
- request_alternate_payment
- send_checkout_reminder
- send_subscription_update_request
- escalate_to_manual_review
- do_nothing

ML MODEL
--------
The checked-in model is a scikit-learn LogisticRegression pipeline with numeric
imputation/scaling and categorical one-hot encoding. It predicts recovery
probability from these 12 pre-outcome features:

amount, customer_age, account_age, previous_successes, previous_failures,
retry_count, checkout_visits, cart_value, subscription_age, event_type,
payment_method, failure_reason

The model was trained on 2,500 synthetic historical events. Approximate
documented holdout performance is 60.6% accuracy and 0.638 ROC-AUC. This is a
demonstration model, not production-grade evidence. The deterministic scorer
is used if the model is missing or inference fails.

LLM
---
Ollama/local LLM generation is optional and runs after a strategy is selected.
The prompt prevents strategy changes, financial authorization, premature
success claims, internal score disclosure, and invented discounts or refunds.
Disabled, unavailable, timed-out, or invalid LLM responses use deterministic
fallback reasoning/templates. The API continues to work without Ollama.

SAFETY
------
AI proposes. Deterministic safety rules authorize.

Fraud Hold, closed-account, and cancellation-intent cases can be forced to:
escalate_to_manual_review

The adaptive policy cannot override these decisions. The frontend disables
execution for escalation, and the simulated gateway independently blocks
terminal retry conditions. Fraud Hold produces manual review, zero recovered
amount, and no gateway retry.

ADAPTIVE POLICY
---------------
The current policy is an in-memory contextual epsilon-greedy policy. Its
decision context includes event type, diagnosis, payment method, probability
bucket, and retry bucket. It updates strategy reward statistics after a
simulation and can choose only from strategies already approved by the
deterministic rules.

It adapts strategy selection only. It does not learn retry delays, channels,
or a full production contextual bandit. Policy state is lost on restart.

RETRAINING AND LEAKAGE CONTROL
------------------------------
POST /recovery/retrain combines the baseline dataset with validated persisted
simulation feedback, trains a candidate LogisticRegression model, and promotes
it only when validation thresholds pass. A rejected candidate does not replace
the current production model.

The training set contains the 12 features above plus recovered as the target.
Outcome-derived fields and operational metadata are excluded, including
recovered_amount, recovery_time, outcome, status, reward, customer response,
gateway references, action details, strategy, identifiers, and decision
context. Missing fields, invalid labels, duplicate simulation IDs, and
financially inconsistent amounts are rejected.

API
---
GET  /health                 Service health.
POST /recovery/analyze       Analyze without execution or persistence.
POST /recovery/simulate      Analyze, simulate, observe, learn, persist.
GET  /recovery/metrics       Return persisted recovery and strategy metrics.
POST /recovery/retrain       Train and conditionally promote a candidate.

DEMO
----
1. Select Payment Failure with network_error.
2. Analyze and show probability, diagnosis, strategy, confidence, score
   factors, and deterministic fallback reasoning if Ollama is unavailable.
3. Execute Recovery and show the simulated recovered amount.
4. Open Learning and Strategy Performance to show feedback and persisted
   metrics.
5. Select Fraud Hold, analyze, and show manual escalation, disabled execution,
   and the deterministic safety explanation.

LIMITATIONS
-----------
- Execution and recovered revenue are simulated, not real settlement.
- Simulation feedback is synthetic and model-influenced.
- The adaptive policy is in memory and is not durable.
- Repeated event submissions are not deduplicated.
- Frontend Simulation and Learning views are current-session views.
- Strategy Performance uses persisted database metrics.
- Vite uses a local /api proxy during development; production needs API URL
  and CORS configuration.
- The ML model uses synthetic data and has modest validation performance.
